## Proven defect and correction

The preexisting `scripts/reassemble_android_delivery.py` validates each downloaded part's SHA-256 and the full reassembled file SHA-256, writes its own `.assembling` file, checks that destination output is absent, then calls `Path.rename(output)`. POSIX rename replaces an existing file **even if another assembler created that destination after the last check**. This violates the script's explicit no-overwrite promise and could destroy a competing process's complete signed file. No actual user data loss was observed; the negative control was synthetic, deterministic and executed against the *real script*.

- **Production fix** [c568e6c6](https://github.com/alwansan/raf/commit/c568e6c6c090c2ade8d15f1c5d70d061ba66940e): after the existing preflight, atomically create a second hard-link name to the completely hash-checked temporary by `os.link(temporary, output)`; if another destination is present, `FileExistsError` becomes a guarded refusal. Delete the owned temporary only after successful atomic publication. This does **not copy multi-GB APK/OBB/XAPK again** and preserves all original ZIP bytes, existing SHA-256 checks and signed payload.

Reassembly on the actual phone/shared storage was **not exercised**; no claim of broad filesystem support.
