# T4 LOCAL-005 — non-mutating Android Save file-state postcheck (2026-11-05)

## What changed in the production Android source stage

The real `scripts/instrument_android_runtime_operations.py` operation wrapper, **after the exact existing SHA authentication of the Android-adapted `SaveAndLoad` original source**, now emits one additional Android-only observation for **only** the original `private void Save(string filename, RGD raftgamedata)` method. This is new evidence for the next device trial, not a save fix or a proof of durability.

In the existing operation wrapper's `finally`, after the original Save method body has run or returned early, it checks `System.IO.File.Exists(filename)`; **only when the file exists** it reads `new System.IO.FileInfo(filename).Length` to classify its size as `zero` or `nonzero`. It records `save/Save.argumentFileSnapshot` with `exists_at_filename_argument=true|false` and `length_class=zero|nonzero|not_checked` plus `durable_RGD_unverified=true`. If the probe cannot complete it records `save/Save.argumentFileSnapshot.unavailable` and the broad exception **type** only. Even if the diagnostic logger throws, bounded catches prevent the new postcheck from masking the original Save return or exception; existing `EndOperation` is still called. The new event does **not** print filename/path, read file bytes, write any file, change .rgd serialization, set world flags or suppress original save errors.

A missing file at this exact argument path is a diagnostic to correlate with the original Save and Load/caughtException events, **not a standalone assertion of save failure**. A present nonzero file is equally **not** a game save success, durable write, correct serialized schema or viable reopen. The recording is Android-only via `#if UNITY_ANDROID && !UNITY_EDITOR`; original code remains unchanged for non-Android.

## Why the filename is grounded in the original compiled game

Prior T4 [actual original FileManager managed stream CI42020039305](https://github.com/alwansan/raf/actions/runs/42020039305) already proved the original compiled FileManager `File.Create` and `File.Open` methods can really write/close/reopen a **synthetic** file on Linux/.NET9 using the SHA-pinned original DLL and 151 managed siblings. [CIL IO call-region CI42019696138](https://github.com/alwansan/raf/actions/runs/42019696138) proved File.Open/Create is the only direct call in either original helper's `try`; its three other transitive callees occur only inside the `catch`, which may return normally. Thus an outer `Save.exit exceptionEscaped=false` **cannot** establish a real file exists.

For the new path check, T4 extended its existing privacy-safe `Mono.Cecil 0.11.5` exact-original oracle in `android-port/Experiments/T4/OriginalFileIoFlow/Program.cs`. It authenticates the **same immutable ZIP2 original Assembly-CSharp.dll**: 3,211,776 bytes, SHA256 `0a6f0527856a9ce538d8d4217358b467c58fdcfad95e0ebebf9588c48f24f72e` from ZIP2 commit `15964ea8f246b6e076ce26b60931ee2e1a9a2385`. It resolves the one original `SaveAndLoad.Save` → `FileManager` write call operand in actual compiled IL, verifies its instance method has the expected first `System.String` parameter, then examines whether the immediately preceding IL instruction forwards original filename argument `ldarg.1`. It emits only the boolean `save_original_filename_directly_forwarded`, not original code, IL offsets, private method symbols or path strings.

[**CI42027197515 — SUCCESS**](https://github.com/alwansan/raf/actions/runs/42027197515): **21/21** fail-closed synthetic controls and genuine original compiled IL. It reports **`save_original_filename_directly_forwarded=true`**, read `File.Open` and write `File.Create` call shapes, same authentic catch placement, plus `original_device_file_io_executed=false`. The new Android snapshot therefore reads the **same unmodified string argument forwarded to the compiled original FileManager writer**, rather than a guessed path.
