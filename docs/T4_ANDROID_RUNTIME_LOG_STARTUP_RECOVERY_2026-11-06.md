## Concrete defect (real code, synthetic fault)

`AndroidRuntimeLog.Initialize` previously returned immediately if either `sink != null` or `StorageError != null`. If initial sandbox directory creation failed (for any transient reason), `PersistentDiagnosticLog` was never created but `StorageError` permanently blocked later explicit `Initialize()` calls, even if filesystem access was restored. This was a source-level vulnerability in diagnostic availability, **not evidence the owner's phone experienced such a fault**.

Added `AndroidRuntimeLog.cs` to existing `Diagnostics.csproj` under `UNITY_ANDROID` with synthetic compile-only `UnityEngineStubs.cs`. No stub is imported into Unity game/native staging. The real source executes through its actual `Initialize`, `Status`, `Flush` and `Shutdown` pathways. The deterministic fault makes `Application.persistentDataPath` resolve to an **ordinary file**; initial initialize sets `StorageError`. The fixture removes the file, creates a directory at that same path, retries, then requires `StorageError==null`, `Status=="ready"`, exactly one primary `raft-*.jsonl` segment after an idempotent third Initialize, an actual persisted `logger.ready` entry and parseable JSONL.
