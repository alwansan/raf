## Actual integrated game source changes
1. `android-port/Runtime/Platform/PhysicalMouseMotionSource.cs`: new independent pure C# `PhysicalMouseButtonWheelFrame`. Android UI captured events only, source validation, ACTION_BUTTON_PRESS=11 / RELEASE=12 and primary DOWN/UP fallback; aggregate button edges into bitmasks so two callbacks for one primary action do not become two Unity presses. Stages press+release even if both occur between two Unity frames. Samples button held/down/up and horizontal/vertical wheel at most once per Unity `Time.frameCount`; resets all pending and last-frame state on native loss/release. Invalid source, unsupported button mask, non-finite scroll, zero scroll, >1000 axes fail closed. Wheel scaling 0.1× Android detent, frame max ±20. No global InputSystem queue or virtual-touch injection.

Wrapper first asks original Unity Legacy Input and returns its real nonzero / true answer; only when it is silent, `requested && nativeCaptured`, returns the per-frame captured source fallback. Editor/non-Android branch directly delegates to original Unity Input with no JNI or pointer capture.
3. `scripts/t4_adapt_original_mouse_buttons_wheel.py`: original managed DLL hash/size authenticated before plan/apply; only exact verified `4+6+2+6+2` direct call sites across original C# source may be replaced. ## Known boundaries and risks to test
- A fallback cannot fix button/wheel events if the Unity focused View never supplies them to `onCapturedPointer`. Real owner CL trace used the old Mini APK and lacked all `capture_request` events, so device input capture is **not proven**. New game artifact must include the source SHA containing this patch and be signed/traceable.
- ACTION_DOWN/UP and BUTTON_PRESS/RELEASE can both describe primary input; bitmask coalescing prevents double-edges in the same Unity frame. Native Legacy Input is **preferred** when present, preventing two logical cursor press or wheel values.
- Wheel scale 0.1 Unity-axis units per Android axis unit is a **provisional calibration**, not tested on device. Compare original Unity `Input.mouseScrollDelta` behavior, menu wheel direction, and horizontal if hardware supports it.
- Unity Editor and Windows/C# builds compile/execute the exact original Legacy Input path. Touchscreen `SOURCE_TOUCHSCREEN` is never promoted to physical mouse or Pointer Capture; existing virtual-touch Mouse0 script is unchanged.
- Capture release while buttons held must clear staged state; stale epoch cannot enter a new generation. Test keyboard, pad input, PC Settings unchanged, mouse camera, save/reopen world and menu focus.
- The source patch fail-closed cardinality might drift when previous Unity pre-build tools rewrite a caller; next *actual* heavy build must confirm authentic original count in staged project and compile gameplay, not just the isolated private DLL. If drift is found, audit the real staged caller safely; do not relax count without proof.
