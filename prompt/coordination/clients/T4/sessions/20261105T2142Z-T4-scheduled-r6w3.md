New distinct risk observed by inspection: `requested` is set before Android UI-thread View.requestPointerCapture and stays true when focus/view checks return early or OS revokes pointer capture. `nativeHasMotion` is set on first captured ACTION_MOVE but is not reset on an Android View.onPointerCaptureChange(false) callback; bridge does not register that callback. `Axis` switches from legacy Input.GetAxis to accumulator whenever `requested && nativeHasMotion`; a revoked capture without Unity focus loss could therefore yield perpetual zero axes (or stale values) until recovery. This is a **source-derived hypothesis**, not a reproduced Android failure. RequestCapture retries every 1.5s and may reacquire; no guarantee of capture acceptance/recovery on the target View.
